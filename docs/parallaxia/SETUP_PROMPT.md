# 依頼: PARSEC47 の現代的リメイクを制作するための「制作環境」を構築せよ

あなたの仕事は、PARSEC47 の現代的リメイクを**後続の制作セッション（以下「制作エージェント」）**が
制作・検証できる環境を、このリポジトリ内に用意することである。**ゲーム本体は実装しない。**
環境が完成し、制作エージェントが最初のタスクに着手できる状態になったら終了する。

## 0. 前提（著者が決定済み）

この依頼書の「著者」は PARSEC47 の原作者本人である。

| 項目 | 値 |
| --- | --- |
| 方針 | 現代的リメイク。原作は参照するが、コードの移植はしない |
| ターゲット | ブラウザの素の Canvas（2D）。ゲームエンジンやフレームワークは使わない。ビルドツールとテストツールの選定は任せる |
| 作業担当エージェント | Claude Code（固定。交互編集はしない） |
| レビュー担当エージェント | 未指定。著者の常用構成では Codex がレビューを担当する |
| 作業場所 | このファイルがあるリポジトリのルート（以下 `ROOT`） |
| 原作資料の場所 | `ROOT/original/`（配置済み。git の管理対象にはしない） |
| ドキュメントの言語 | 日本語（コード中の識別子とコメントは英語でよい） |

このリポジトリは後で別の場所へ移動される。**絶対パスをファイルに書き込まず**、`ROOT` からの相対パスだけを使うこと。

### 原作資料を制作の資料と分けて置く理由

理由は一つだけである。**制作エージェントの設計が原作のコード構造に固定されるのを避けたい。**
法的な制約ではない（原作は BSD 2-Clause で、利用は自由である）。したがって境界は次のように引く。

- 渡してよいもの: 挙動の説明、設計意図、数値（速度、間隔、耐久力、得点式など）、実測値、画面写真
- 渡さないもの: コードの転記、クラス構成・ファイル構成・処理順をそのままなぞった説明

判断に迷ったら、「これを読んだ制作エージェントが、原作と同じ構造のコードを書きたくなるか」で決める。

### `agentic-gamedev.md` の扱い

`ROOT/agentic-gamedev.md` は、著者が別のリポジトリ（小さな新作ゲームを量産する場所）で使っている指示書であり、参考資料である。
このリポジトリの指示書ではない。次のように扱う。

- そのまま適用しない。`tools/pick-tags.mjs`、`tools/snapshot.mjs`、`tools/check-done.mjs`、`tmp/games/<slug>/`、タグの抽選、コンセプト立案の工程は、このリポジトリには存在せず、適用もしない。
- 次の考え方は `CLAUDE.md` に翻案して取り込む（Phase 4）。
  - 小さく作って人間が触って判断する（スライス先行。面白さをエージェントが採点しない）
  - 模擬プレイヤーは方策のはしごで使う（強い方策は抜け道の検出と圧力の基準、人間並みに制限した方策は難易度の確認）
  - 描画や音だけを変える変更は、シード付きシミュレーションの結果を変えてはならない
  - 人間に渡したビルドは後から再現できるように残す
  - 仕上げ段階に入ったら `REVISION_HISTORY.md` に経緯を残す
  - スモークテストだけでは、意図した遊びが成立している証拠にならない

## 1. 対象について分かっていること

### 著者の言明（検証不要）

- PARSEC47 は ABA Games（Kenta Cho）の作品で、2003-11 にリリースされた。Windows 向けのフリーウェアで、最新版は 0.21。
- 最新版の配布ページ: https://www.asahi-net.or.jp/~Cs8K-Cyu/windows/p47.html
- 配布 zip（ver. 0.21、2018-01-20）にはソース（`src/`）、BulletML の XML、画像、音声、Windows 用の実行ファイルが含まれる（2026-10-07 に確認）。
- 原作のライセンスは BSD 2-Clause であり、利用は自由である（2026-10-07 の言明。条文は配布物の readme にある）。
  原作のコードや素材を再配布する場合は、著作権表示と条文を添える。

### 出発点（検証し直すこと）

- 著者の紹介ページ: https://www.asahi-net.or.jp/~cs8k-cyu/windows/p47_e.html
  - "retromodern hispeed shmup"。スローキーを押している間は自機が減速し、ロールショットとロックオンレーザーが使える。
  - 使用技術は D、OpenGL、SDL、SDL_mixer（Ogg Vorbis）、libBulletML、Mersenne Twister。
- 第三者のフォーク https://github.com/M-HT/parsec47 は、D2・SDL2・Linux・Pandora・Pyra へ移植されている。
  敵ごとの BulletML ディレクトリ（small/, middle/, large/, morph/, *_lock/, *move/ など）、images/、sounds/ を含む。
  同梱の readme は原作のもので、履歴の最新は ver. 0.2 である（2026-10-07 に確認）。0.21 との差分は未確認。
  フォークで加えられた変更部分のライセンスは未確認。
- Debian パッケージ `parsec47` がある。著者のブログに 2003-12-01「PARSEC47をビルドする方法」（https://aba.hatenablog.com/entry/20031201/p1）がある。

### 未確認の事項

- M-HT フォークと原作の差分の範囲
- 同梱ライブラリ（libBulletML、Mersenne Twister など）のライセンス
- 原作の各メカニクスの正確な仕様

著者に聞けば分かる事項（原作の配布物の中身、設計意図など）は、推測で埋めずに質問として列挙する（§5）。

## 2. 資料の置き場所の規則

| 場所 | 中身 | 制作エージェントの扱い |
| --- | --- | --- |
| `ROOT/reference/` | 著者ページの本文、操作説明、メカニクスの仕様メモ（数値を含む）、弾幕の説明、画面写真 | 読んでよい。制作の一次資料とする |
| `ROOT/original/` | 原作の配布 zip とその展開物（ソース、BulletML の XML、素材、実行ファイル）、M-HT フォーク | 既定では開かない。下の条件でだけ調べる |

- `reference/` の文書は、§0 の境界に従って書く。挙動と数値は書く。コードは貼らず、原作の構造もなぞらない。
- `reference/` の各文書には、根拠にした原作側のファイル名を書いてよい（後で確かめ直せるようにするため）。
- 制作エージェントは、`reference/` に必要な事実（数値、発生条件、順序）が無いときに限り、その事実を原作資料で調べてよい。
  調べた結果は `reference/` に追記してから使う。原作のコードを読んで設計の参考にすることはしない。
- プレイ動画はダウンロードしない。URL と、見て分かったことを `reference/` に記録する。
- 原作の素材（画像・音声・BulletML の XML）をリメイクで使うかどうかは未決定である（Phase 4 の `docs/remake-decisions.md`）。
  決まるまで `original/` の外へはコピーしない。

## 3. 実行環境についての注意

- Bash はサンドボックス内で動き、書き込めるのは `ROOT` 配下だけである。`ROOT` の外へは書き込まない。
- Bash から届くホストは限られている（GitHub、npm など）。それ以外のホストが必要なときは、その都度許可を求める。
  Web ページの閲覧には Web 取得・検索のツールを使う。
- `sudo` は使わない。システムパッケージの導入が必要な作業は、必要なパッケージ名を記録して飛ばす。
- 読み書きするのは `ROOT` 配下だけとする。例外は、ツールチェーン・パッケージのキャッシュ・導入済みスキルの読み取りである。
- コミット、ブランチ作成、index の変更はしない（著者が行う）。`.gitignore` は用意し、`original/` を含める
  （検索ツールが原作のコードを拾わないようにする意味もある）。

## 4. フェーズ（順に実施し、各フェーズの終わりに `research/setup-log.md` へ記録を残す）

### Phase 1 — 調査と資料の整理

- 一次資料、原作のソース、フォーク、Debian のパッチ、著者のブログ記事、プレイ動画を調べる。
- 調べた内容は `research/provenance.md` に記録する。形式は「主張・出所（URL またはファイル）・取得日・確度（著者の言明／確認済／推測）」とする。
  確認できなかった事項は「未確認」と書く。
- ライセンスは `research/licenses.md` にまとめる。調べる対象は、M-HT フォークの変更部分と同梱ライブラリである。
  原作は「BSD 2-Clause（著者の言明、配布物の readme）」と書けば足りる。
- 原作の配布 zip（ver. 0.21）は `original/p47_0_21.zip` に取得済みで、`original/p47_0_21/` に展開してある。
  追加で取得した原作資料（M-HT フォークなど）も `original/` に置き、中身の一覧を `original/INDEX.md` に作る。
- §2 の規則に従って `reference/` を書く。最低限、次を含める。
  - 操作とメカニクスの仕様メモ（自機、通常ショット、スロー、ロールショット、ロックオンレーザー、敵の種類、ランク、得点、残機）
  - 弾幕の構成の説明（敵の種類ごとにどんな弾幕があり、どう組み合わされるか）
  - 画面写真（著者ページのもの。取得できなければ URL）
- JavaScript／TypeScript の BulletML 実装（既存のもの）を調べ、候補とライセンスと保守状況を `research/bulletml-js.md` に記録する。
  採用するかどうかは決めず、選択肢として記録する。

### Phase 2 — Canvas の土台と計器

- 空の実行可能プロジェクトを作る（ゲーム内容は不要）。キャンバスに 1 フレーム描画できれば十分である。
- 構造上の要件は次の二つである。
  - シミュレーション（状態の更新）は DOM に依存させず、Node 単体でも実行できるようにする。Canvas は描画だけを担当する
  - ブラウザ側にはデバッグ用のハンドル（例: `window.__game`）を一つ用意し、状態の読み書き、1 フレーム進める操作、シードの指定、入力の注入をそこから行えるようにする。
    このハンドルは検査の土台なので、契約として README に書く
- 次の計器を用意する。導入済みスキルに同梱のスクリプトや雛形があるものは、それを使う（自作し直さない）。
  1. 固定シードと入力リプレイによる決定的な実行（ゲームループは固定タイムステップ）。
     同じシードと入力から同じ状態ハッシュが得られることを検査する。描画や音だけの変更でこのハッシュが変わらないことを、後で確認できるようにする
  2. ヘッドレスブラウザによるスモークテスト（`smoke-testing-web-games` の `smoke-test.mjs`）。起動・放置・入力の各段階で、コンソールエラーとクラッシュを検出する
  3. 指定したフレームのスクリーンショットを取得するコマンド
  4. 状態を注入してメカニクスを検査するテストの雛形（`probing-web-game-mechanics` の `probe-template.mjs` を元にする。例: スロー中にだけロックオンが発生する）
  5. 弾の軌跡のトレース出力形式（フレーム、弾の識別子、位置、方向、速度）。弾幕記述の形式は未決定なので、ここでは出力形式だけを定める。
     読み込み側の実装は BACKLOG のタスクとする
  6. 方策ごとのスコアを比べる枠。単調な方策（放置・押しっぱなし・連打）、探索的な方策、人間並みに制限した方策（反応の遅れ、タイミングの誤差）を差し込めるようにし、
     スコア比（exploratory_ratio）を `evaluating-gameplay-balance` のログ形式で出す。
     これは退化を検出するものであり、面白さを判定するものではないと README に明記する
  7. 追跡対象のファイルに絶対パスが含まれていないことの検査
- すべての検査をワンコマンドで実行できるようにする。
- 計器そのものを確かめる。各計器について、わざと壊したフィクスチャで**失敗する**ことを確認する
  （例: 入力でクラッシュするページをスモークテストが検出する。乱数を固定していない実行を決定性の検査が検出する）。
- ゲーム内容が無いために検査できない項目（計器 4 と 6）は、成功ではなく「未実装のためスキップ」と表示させる。
  検査を緑にするためにゲームのロジックを書かない。

### Phase 3 — 制作エージェント向けの指示ファイル

- `CLAUDE.md` に次の内容を書く。
  - 目的、方針（現代的リメイク）、資料の扱い（§0 の理由と境界、§2 の規則）
  - 作業担当は固定であること。レビュー担当が指定された場合は、その結果を作業担当へ返すこと
  - `agentic-gamedev.md` から翻案した項目（§0 に列挙したもの）
  - 使うスキルと使う場面。例: smoke-testing-web-games、probing-web-game-mechanics、evaluating-gameplay-balance、
    maximizing-game-feel、implementing-gameplay-invariants、adversarially-validating-game-repairs、
    directing-game-visuals、building-era-authentic-game-audio。
    これらはユーザー単位で導入されたプラグインに含まれ、リポジトリには入っていない。
    導入元（マーケットプレイスとプラグインの名前）を調べて書いておく
  - デバッグ用ハンドルの契約。ルールが依存する状態は、必ずこのハンドルから届くようにする
  - 仕様が曖昧なときの扱い。Assumptions として明記したうえで進め、黙って決めない
  - 面白さはエージェントが判断しない。人間が 1 プレイ触って判断する。そのために、区切りごとに次の二つを提出する
    - プレイできるビルド
    - 「このゲームがプレイヤーに求めているプレイ」を一文で書いたもの
  - 作業の最後には必ず全検査を実行する
  - コミットなどの Git 操作は、指示されたときだけ行う
- `AGENTS.md` を作り、`CLAUDE.md` を読むように一行で案内する（レビュー担当が Codex の場合のため）。
- `BACKLOG.md` はセッションをまたいで作業を続けるためのファイルとする。最初のタスク群を案として置く
  （自機の移動 → 通常ショット → スロー → ロールショット／ロックオン → 敵 1 種＋弾幕 1 種 → …）。
  順序の最終決定は人間に委ねる。
- `docs/spec-draft.md` には、`reference/` を元にした仕様の叩き台を書く。不明な点は「未確定」として列挙する。
- `docs/remake-decisions.md` には、リメイクとして著者が決めるべき点を列挙する。例:
  - 弾幕の記述方法（BulletML を使うか。使うなら原作の XML を流用するか、書き直すか）
  - 画面比率
  - 操作系（キーボード／ゲームパッド／タッチ）
  - 描画の方向性（原作のベクター調の線画を踏襲するかどうか）
  - 音（原作素材を使うか、algo-chip や sounds-some-sounds 等で作り直すか）
  - 難易度とランクの扱い
- `README.md` を、構築後の状態に合わせて書き換える。

### Phase 4 — 参照実装を動かす（任意。Phase 3 まで終わってから着手する）

目的は、手触りに関わる値（自機の速度、弾の密度と速度、敵を倒すのにかかる時間など）を実測して `reference/` を補うことである。
フレーム単位でリメイクと一致させるための比較ではない。

- 作業ディレクトリは `original/` 内とする。
- 次の順に試み、進めなくなった段階で止める。
  1. M-HT フォーク（Linux/SDL2）のビルド、または Windows 版の実行（この環境は WSL2 なので、Windows 側で直接実行できる可能性がある）
  2. 画面写真の取得
  3. 状態ログ（フレーム、自機、敵・弾の数、スコア）の取得。原作のソースへの改造が必要になる
- ビルドに必要なコンパイラやライブラリが無く、`sudo` なしで導入できない場合は、必要なものを記録して終える。ここに時間をかけない。

## 5. 禁止事項

- ゲーム本体のロジックを実装しない。
- 原作のコードを `original/` の外のファイルやコメントへ転記しない。原作の構造をなぞった説明も書かない（§0）。
- 原作の素材を `original/` の外へコピーしない（使うかどうかが未決定のため）。
- 推測を事実として書かない。確認できなかったことは「未確認」と書く。
- 絶対パスを書き込まない。
- `ROOT` の外に書き込まない。

## 6. 完了報告（最後に提出するもの）

1. 作成したファイルの一覧と、それぞれの役割
2. ワンコマンドで検査を実行した結果（ログ付き）。計器ごとに、壊したフィクスチャで失敗を確認できたかどうかも書く
3. 飛ばした作業と、その理由（サンドボックス、ネットワーク、不足しているパッケージ）
4. 参照実装の稼働状況（どの段階まで進んだか）
5. `research/provenance.md` に記録した未確認事項のリスト
6. 著者への質問（著者に聞けば分かる事項）
7. `docs/remake-decisions.md` のうち、制作を始める前に著者が決める必要のある項目
