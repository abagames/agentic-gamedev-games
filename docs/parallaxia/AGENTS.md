# PARALLAXIA（PARSEC47 リメイク）— 制作の指示

## 目的

PARSEC47（ABA Games、2003）の現代的リメイク「PARALLAXIA」を、ブラウザの素の Canvas（2D）で作る。
原作は参照するが、コードの移植はしない。ゲームエンジンやフレームワークは使わない。

経緯は `REVISION_HISTORY.md` にある（リポジトリのほかのゲームに合わせて、この文書だけ英語で書く）。セッションの最初に読み、何かを変えたら、そこに書き足す（観察、原因、変えたこと、根拠。採用しなかったものと、測っていないものも）。

### 置き場所

このプロジェクトは、リポジトリ agentic-gamedev-games の `docs/parallaxia/` にある。完成までは `parallaxia` ブランチで開発し、2026-10-12 に 1 コミットにまとめて main に入れた（写しを含む途中の履歴は、公開していない）。
この文書のパスとコマンドは、すべてこのディレクトリを基準にしている（リポジトリのルートから検査を走らせるなら `npm --prefix docs/parallaxia run check`）。

リポジトリのルートにある `AGENTS.md` は、`docs/` 以下を完成品として扱い、新しいゲームを `tmp/games/<slug>/` に作る前提で書かれている。
**このプロジェクトはその例外である（著者の決定、2026-10-10）。** ここでの作業は、この文書（`docs/parallaxia/AGENTS.md`）に従う。ルートの `AGENTS.md` と食い違うところは、この文書を優先する。

- ルートの `AGENTS.md` のうち、ここに適用しないもの: `docs/` 以下を書き換えないという規則、`tmp/games/<slug>/` という置き場所、タグの抽選、コンセプト立案の工程、ルートの `tools/`（`pick-tags.mjs`、`snapshot.mjs`、`check-done.mjs` など）。
  写しと検査には、このディレクトリの `tools/` を使う
- ルートの `AGENTS.md` は書き換えない。`docs/` 以下のほかのゲームと、ルートの `README.md` のゲーム一覧にも、指示されない限り触れない
- `node_modules/`、`original/`、`artifacts/`、`replays/`、`snapshots/`、`docs/looks/`、`reference/screenshots/*.gif` は、このディレクトリの `.gitignore` で外している。写しとリプレイなどの確認用のデータは公開しない（著者の決定、2026-10-12。`snapshots/` はそれまで git に入れていた）。写しは手元にだけあるので、消すと取り戻せない。`replays/` は著者のプレイの記録で、著者の決定（2026-10-12）で公開しない。手元にだけある

### 著者が決めたこと（要点。全体は `docs/remake-decisions.md`）

- 狙い: 原作の核を残して作り変える。核は **高速で、避けるのが爽快な弾幕** である
- 原作から良くしたい点: **敵への打ち込み感や破壊などのゲームフィール**
- モードは LOCK だけ。ロックオンは「ショットを押している間にたまり、離すと発射」の形にする（原作の「押している間ずっと撃つ」ではない）
- 画面は縦長（フィールドだけを画面いっぱいに使う）。見た目は 1980 年代ラスター風で、キャラクターは大きめ
- スローは無い。入力は移動とショットだけである。ヒットストップも入れない
- フィールドは画面より広く、自機の左右移動に応じて画面が少しスクロールする。画面外の敵は弾を撃たない（画面の位置は遊びの規則なので、シミュレーションの状態 `viewX` にある）
- 操作はキーボード（矢印と WASD）、ゲームパッド、タッチ。タッチは片手の 1 本指で遊べること。PC とモバイルで同じ遊びにする。キーボードのショットはオートにしない
- 弾幕は、原作の構造（型のランダム生成、弾が弾を撃つ変化）を踏襲し、中身は原作の XML を参考に書き直す。JavaScript のデータとして `src/sim/barrage.js` にある（BulletML は使っていない）
- 弾の「種」は撃った敵に乗って動き、敵を倒すと種も消える
- 敵弾は原作より速くする（いまは 1.6 倍）
- アイテムは無い。ショットは前方のみ。見た目は自機の幅いっぱいのツインショットだが、扱いは幅のある 1 発である（2 本が別々に当たることはない）。画面上に同時 4 発・3 フレームに 1 発（原作の毎フレーム 1 発・同時 32 発は強すぎた）。敵の本体に触れるとミス（体当たり）。得点は編隊全滅ボーナスの連鎖（2026-10-10 決定、実装済み。細部の値は仮定で、`docs/spec-draft.md` §7・§9・§10 にある）
- 小型の敵は編隊で、21 種の飛行パターンのどれかを飛ぶ。中型は 8 種、大型は 7 種の飛び方を持つ。飛行パターン・飛び方・弾幕の形・ボスの動きは、周回ごとに少しずつ解禁され（`UNLOCK`）、二巡目からは性格のある区間（SWARM、HEAVY、ISLANDS）が混ざる。新しいものを足すときは、一覧の末尾に足す（途中に入れると、固定した SECTOR の中身が全部ずれる）。仕様は `docs/flight-patterns.md` にある。左右に動くもの（サイン、ジグザグ、横断）は著者の指示で足した。最初の 10 種のうち 6 種は自機の位置に反応する（読むのは区間の変わり目の一瞬、x だけ。急降下だけは y も読む）。敵の形は飛行パターンで決まり、区間が進むごとに 1 種ずつ加わる。著者の判断で、いまの飛行曲線と弾幕に問題のあるものは無いものとして扱う。弾が分かれるのは、撃った敵の近くで、短い時間のうちに終わらせる（長く飛んでから分かれる弾幕は抑える。著者の指示）
- 決めずに置いたもの: ルールの改良（`REVISION_HISTORY.md` の「Not adopted」）。完成の時点で、どれも入れていない
- 中型と大型は役割を分ける（著者の指示）。中型は柔らかく（耐久 16）、軽武装（分裂する弾は撃たない）で、4 種の遅い飛び方をする。大型は以前のまま、まっすぐ沈み、弾幕を張る
- 小型敵の弾幕は 1 発ずつの単純なものに保ち、難度は発射頻度と弾の速さ（`SMALL_FIRE`）で先に調整する（著者の指示、2026-10-10）。形を複雑にして難しくしない。中型・大型・ボスも、弾は速くまばらにし（`MIDDLE_FIRE`、`LARGE_FIRE`、`BOSS_FIRE`）、画面に留まる遅い弾は作らない（`BULLET.minSpeed` が下限）
- 全体の構成は、無限 SECTOR 制と 3 つのモード（CLOSE、CHAIN、GRAZE）である（著者の決定、2026-10-10）。モードは敵弾の速さ・密度と自機の速さだけを変え、SECTOR の中身は共通。到達した 10 ごとの SECTOR から始められ、開放は 3 モードで共通（あるモードで詰まっても、別のモードで先へ進める）。自機は全般に遅めにしてある（著者の指摘）。敵弾や自機の速さを変えるときは、3 モードとも測り直す（`docs/spec-draft.md` の「全体の構成」）
- 得点は「撃破の点数 × 倍率（x1〜x16）」で、編隊ボーナスは無い（著者の決定、2026-10-10）。倍率の稼ぎ方はモードごと: CLOSE は接近、CHAIN は編隊全滅の連鎖、GRAZE は敵弾へのかすり（`docs/spec-draft.md` §7、`src/sim/score.js`）。連鎖（`sim.chain`）があるのは CHAIN だけなので、連鎖の検査や計測は CHAIN で行う
- BGM がある（著者の指示、2026-10-11）。ファミコンの 5 チャンネル（矩形波 2、三角波、ノイズ、DPCM）の制約で書いた曲データを、効果音とは別の音源として鳴らす（`src/audio/music.js`、`docs/audio.md` の「BGM」）。曲は耳で確かめていないので、良し悪しを述べない
- SECTOR の中身は固定である（著者の決定、2026-10-10）。何が・どの順で出るかは SECTOR 番号から決まり、プレイごとに変わるのは位置と機数だけ。敵や弾幕の規則を変えると、全 SECTOR の中身が変わるので、変えたあとは SECTOR ごとの点検（`docs/spec-draft.md` の「SECTOR の中身の固定」）をやり直す
- 地形は、いろいろな並べ方で流れる地上物である（著者の指示、2026-10-11。スターフォースを参考）。**地上は点数だけ**で、連鎖にも倍率の保持にも関わらず、逃がしても何も失わない（だから配置は自由に作れる）。パネル、ボーナスの組、壁、隠れた的、コアがあり、並べ方と特別なものの位置は SECTOR ごとに固定。エクステンドが隠れた的や、手順で現れる高得点の的は入れない（著者の決定）
- ボスがいる（著者の指示。原作の規則に沿う）。一巡の 5 区間目が中ボス、10 区間目が大ボスで、翼を個別に壊せる。耐久と弾幕の強さは自前の値
- 音は手続き的に生成する（効果音とジングルは実装済み。`docs/audio.md`）
- 「任意」とされた項目（弾幕の記述方法、難易度の段階、残機、言語とビルド）は、制作エージェントが決めてよい。
  決めたら Assumptions として報告し、`docs/spec-draft.md` を直す

## 資料の扱い

| 場所 | 扱い |
| --- | --- |
| `reference/` | 制作の一次資料。まずここを読む |
| `docs/spec-draft.md` | リメイクの仕様の叩き台。「未確定」の項目は決まるまで実装しない |
| `docs/remake-decisions.md` | 著者の決定。エージェントが「決定」の欄を書き換えるのは、著者がチャットで決定を伝えたときだけで、日付と経緯を添える |
| `original/` | 原作の配布物（ソース、弾幕の XML、素材）。**既定では開かない** |

原作を分けて置いている理由は一つである。**設計が原作のコード構造に固定されるのを避けたい。** 法的な制約ではない（原作は BSD 2-Clause）。

- 原作から受け取ってよいもの: 挙動、設計意図、数値、実測値
- 受け取らないもの: コードの転記、クラス構成・ファイル構成・処理順をなぞった設計
- `reference/` に必要な事実（数値、発生条件、順序）が無いときに限り、その事実だけを `original/` で調べてよい。
  調べた結果は `reference/` に追記してから使う。設計の参考にするために原作のコードを読まない
- 原作の素材（画像・音声・XML）を `original/` の外へコピーしない。使うかどうかは未決定である

## 進め方

- **小さく作って、人間が触って判断する。** 著者の指示を 1 つずつ進め、遊べる区切りごとに止まる
- **面白さはエージェントが判断しない。** 有望かどうかの評価も書かない。区切りごとに次の二つを提出する
  1. プレイできるビルド（`npm run serve` で開ける状態。`node tools/snapshot.mjs <ラベル>` で写しを残す）
  2. 「このゲームがプレイヤーに求めているプレイ」を一文で書いたもの
- 完了報告には、すでに見えている構造上の弱点と、検査していない挙動を書く。難易度は、人間のプレイ報告があるまで「未調整」と書く
- **仕様が曖昧なとき**は、Assumptions として明記したうえで進める。黙って決めない。著者が決める事項（`docs/remake-decisions.md`）に当たるなら、仮の値で進めて、仮であることを書く
- 要素を足す前に、いちばん弱い判断・相互作用を直す。数値（速度、出現数、得点）を上げる前に、構造を直す
- 人間のプレイ報告とボットの結果が食い違ったら、プレイ報告を優先する
- 経緯は `REVISION_HISTORY.md` に残す。書くのは、意図、見つけた問題とその原因と根拠、試して採用しなかったもの、測っていないものである

## 構造の規則

- **シミュレーションは `src/sim/` に置き、DOM・時計・`Math.random` に触れない。** 状態はプレーンなデータ 1 個で、`stepSim(sim, input)` だけが進める。
  乱数は `src/sim/rng.js` を使う。これが崩れると、リプレイと状態ハッシュの検査が意味を失う
- **シミュレーションでは `Math.sin`・`Math.cos`・`Math.atan2`・`Math.hypot` などを使わず、`src/sim/math.js` を使う。**
  これらは JavaScript の実行環境によって最後の 1 ビットが違うことがあり、実際に Node と Chromium で `atan2` の結果が食い違ってリプレイが壊れた。
  四則演算と `Math.sqrt`、`Math.abs`、`Math.floor` などは使ってよい。描画側は制限しない
- 音は `src/audio/` に置き、演出と同じく `sim.events` から鳴らす。シミュレーションの出来事を足したら、`src/audio/kit.js` に、音か、理由を添えた「なし」を必ず書く（書かないと単体テストが失敗する）
- 演出は `src/render/fx.js` に置き、シミュレーションが出す出来事（`sim.events`）から起こす。演出に要る情報が足りなければ、出来事を足す。シミュレーションに演出用の状態を持たせない
- 描画（`src/render/`）と音は状態を読むだけで、書き換えない。**描画や音だけを変える変更は、シード付きの実行結果（状態ハッシュ）を変えてはならない**
- ルールが依存する状態は、必ずデバッグ用ハンドル `window.__game` から届くようにする。フレーム内のローカル変数に埋もれたルールは検査できない。
  ハンドルの契約は `README.md` にある。項目を足したら README も直す
- メカニクスを実装したら、`src/sim/sim.js` の `capabilities` に宣言する。宣言されるまで、対応する検査は「スキップ」と表示される
- 絶対パスをファイルに書かない。このディレクトリは移動される

## 検査

**作業の最後に必ず `npm run check` を実行し、結果を報告に含める。** 失敗を残したまま終えない。スキップは理由とともに報告する。

| 検査 | コマンド | 何を見るか |
| --- | --- | --- |
| 全部 | `npm run check` | 下のすべてと、各計器の自己検査 |
| 単体テスト | `npm test` | 決定性、リプレイ、トレース形式、方策比較の枠、パスの検査 |
| スモークテスト | `npm run smoke` | 起動・放置・入力でエラーやクラッシュが出ないか |
| メカニクスの検査 | `npm run probe` | 状態を注入して、仕様どおりの値になるか（`probes/*.probe.mjs`） |
| 方策の比較 | `npm run balance` | 単調な方策と探索的な方策のスコア比。退化の検出であり、面白さの判定ではない |
| 画面写真 | `npm run screenshot -- --frame 120 --seed 1` | 指定フレームの画面を保存する |
| 弾幕の検査台 | `npm run trace -- --loop 2 --type 7` | 生成された敵の型 1 つの弾幕を単体で動かし、構成と弾数を見る |
| 飛行パターンの比較 | `node tools/flight.mjs --seeds design` | パターンごとの軌道の数値と、視界に制限のあるボットでの結果。基準は `docs/flight-eval.md`。最終比較用のシードは、基準を変えずに新しく取る |
| 避けられないミスの検出 | `node tools/dodge.mjs --starts 31,91,151 [--room 2]` | 方策のミスを 0.5〜3 秒巻き戻し、生き残る動き方があったかを探す。弾幕が逃げ場を残しているかを見る。弾をすり抜ける道は数えない |
| 人のプレイの数値 | `node tools/replay-stats.mjs replays --policies author,keeper` | `?rec=1` で保存したリプレイを、遊んだビルドの規則で再生し、入力の頻度・位置・弾との距離・ミスの原因を出す。方策に同じ場面を遊ばせて横に並べる（`README.md` の「人のプレイの記録」） |

- スモークテストが通っても、遊びが成立している証拠にはならない。メカニクスを足したら、その仕様を具体的な値で確かめるプローブを書く
- 検査を通すためにゲームの挙動を曲げない。検査が間違っているなら検査を直し、そう報告する
- 実行していない検査を「確認した」と書かない

### 模擬プレイヤー

- 方策は目的で使い分け、結論がどの方策に基づくかを書く
  - 強い方策: 抜け道と退化した戦略の検出、ゲームがかける圧力の基準
  - 人間並みの方策 `author`（`tools/policies/author.mjs`）: 難易度とテンポの確認。著者のリプレイ 3 本（`replays/`）に合わせてある。合い具合と、合っていないところ（CLOSE で著者より弱い、一巡目のミスが多い）は `docs/human-bot.md` にあり、結論を書くときはそれを差し引く
- 正確すぎるボットは人間を過大評価し、判断の弱いボットは過小評価する。どちらの向きにも外れうる
- 結果を信じる前に、ボット自身を確かめる（入力の頻度が人間にできる範囲か、やられ方がもっともらしいか）
- 連鎖や得点の配分を調べるときは、連鎖を守るように動く `keeper`（`tools/policies/keeper.mjs`、比較は `node tools/chain.mjs`）を使う。それでも著者より連鎖を切らすので、連鎖が切れやすい根拠にはしない
- 人間並みの方策を直すときは、著者のリプレイ（`?rec=1` で保存したもの。`replays/` に置く）と `node tools/human-fit.mjs` で並べ、数値の離れているところから直す。数値を動かしても近づかないときは、仕組みが合っていない（`docs/human-bot.md` の「採用しなかったもの」）
- 入力の変化を遅らせるだけの `humanLimited` は、著者より 3〜7 倍ミスが多い。難易度の根拠にしない
- 方策は `tools/policies/` に足す。`seeker` と `keeper` は、画面を遅れなく正確に見ているので人間より強い。難易度の話には `author` の結果を使う
