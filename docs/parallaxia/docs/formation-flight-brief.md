# 依頼: 小型の敵の飛行パターンを 8 種類、設計・実装・評価せよ

段階 2 の依頼文である。著者の依頼文（2026-10-10）を、このゲームの事情に合わせて直した。
直した点は末尾にある。前提となる段階 1（`docs/formation-plan.md`）が終わってから実行する。

---

縦スクロールシューティングの、小型の敵の編隊の飛行パターンを 8 種類、設計・実装せよ。
スターフォースをプレイフィールの参考とするが、軌道は独自に設計する。

目的は、動きを自然に読め、不意打ちを避けながら、少しのリスクを取れば編隊全滅を狙えることである。

## 設計条件

- 直線、斜行、急転回、停止、加減速、反転、曲線を使い分ける。全案を曲線にせず、振幅変更や左右反転を別案として数えない。
- 自機位置を使う場合は、参照する時点と座標成分を明示する。常時追尾に偏らず、誘導して避けられる余地を残す。
- 転回条件は、位置関係や予兆から読めるものにする。必要な急転回を一律に滑らかにしない。
- 敵ごとに迎撃機会を作るだけでなく、自機が移動可能な順序で迎撃機会をつなぐ。左右への過剰な往復を要求しない。
- 接近して撃てる時間と、敵弾・体当たりが迫る時間を調整する。安全すぎる敵と、ほぼ被弾必須の敵を避ける。
- 画面端、前進した自機、撃ち逃し、複数編隊の重なりでも検討する。

### このゲームに固有の条件

- **スクロール**: フィールド（幅 28）は画面（幅 22）より広く、画面は自機の左右の位置に応じて動く。画面の外にいる敵は弾を撃たない。
  「画面端」は、フィールドの端と、画面の端（自機の移動で変わる）の両方について検討する。自機の移動で編隊が画面から出入りする場面を含める。
- **弾の出方**: 弾は最初の 24 フレーム、当たらない「種」として撃った敵に乗って動き、その後に敵の位置から飛び出す。種のうちに敵を倒すと種も消える。
  射撃規則と、予兆から回避期限までの余裕は、これを前提に定義する。
- **ロックオン**: ショットを押している間にロックがたまり、離すとレーザーが出る。小型はロックできない。
  編隊を撃ち続けたい場面と、中型・大型へレーザーを放つためにショットを離したい場面の重なりを検討する。
- **編隊全滅ボーナス**: 編隊の全機を倒すとボーナスが入り、続けると上がる。1 機でも逃がすと切れる。各案について、最後の 1 機を追う動きが何を要求するかを書く。
- **中型・大型の弾幕**: 現状のままとする。編隊だけの場面に加えて、中型または大型の弾幕が同時にある場面でも検討する。
- **ランク**: 一巡（10 区間）ごとにランクが上がる。各案について、ランクで何が変わるか（速度、発射の頻度、編隊の機数）を定義する。変わらないなら、そう書く。
- **操作**: キーボード（8 方向、一定の速度）と、タッチ（指の動きに自機の速度で追従。指を離すと止まり、ショットも離れる）の両方で成立すること。

## 実装条件

座標系、自機速度、弾速、連射間隔、同時発射上限、当たり判定を明示する。確認値と仮定値を区別する。

- **確認値**は、このゲーム自身の定数である（`src/sim/constants.js`）。段階 1 のあとの値を使う。
  参考: フィールド x ±14・y ±16、画面の幅 22、自機の速度 0.6／フレーム、ショットは前方へ毎フレーム 1 発・同時 32 発・弾速 1、
  弾の当たる半径は約 0.45、敵弾の速さは一巡目でおよそ 0.2〜0.3／フレーム、60 フレーム毎秒。
- **スターフォースに由来する値や印象は、すべて仮定として扱う。** 確かめた数値は手元に無い。調べた場合は出所を `research/provenance.md` に書く。

各案に、区間、速度、転回条件、予兆、編隊数、出現間隔、射撃規則、退場条件を定義する。
曲線の形と時間進行を分離し、意図しない加減速や位置の飛びを防ぐ。

実装は `src/sim/` に置く。シミュレーションの規則（DOM・時計・`Math.random` を使わない、三角関数は `src/sim/math.js`）に従う。
各案について、仕様を具体的な値で確かめるプローブを書く。

## 評価条件

次を別々に評価し、平均生存率だけで採用を決めない。

1. 初見・経験後の次動作の予測可能性
2. 予兆認識から回避期限までの余裕
3. 不意打ちによる死亡
4. 迎撃できる位置と時間の幅
5. 編隊全滅率
6. 全滅優先と生存優先の追加リスク
7. 操作時刻・位置を少しずらした際の成功率

ボットは観測遅延、判断間隔、認識誤差を持ち、未来の軌道や未発射の弾を参照しない。
単独編隊と混合編隊を、複数の初期位置・操作能力・乱数 seed で試す。
ボットで測れない人間の予測や快適さは、未検証と明記する。

- いまある人間並みのボット（`tools/policies/` の `humanLimited`）は、著者の感想と合っておらず、人を過小評価している。
  ここで求めるボットは作りが違う（出力ではなく観測を遅らせる）ので、新しく書く。
- ボットの結果は、8 案の間の比較に使う。全滅率などの絶対値を「人間ならこうなる」と読まない。
- 項目 1（予測可能性）は、ボットでは直接測れない。代わりに測れるもの（たとえば、過去 N フレームの動きからの外挿と、実際の位置との差）を定義し、
  それが人間の予測の代用にすぎないことを書く。

問題があれば局面を特定して調整する。
全滅に自機性能を超える移動が必要な案、予兆なしに回避不能となる案、修正すると特徴を失う案は却下する。

### 採用基準と評価用 seed

**最終比較の前に固定する。** 固定した基準と seed は、結果を見る前に `docs/` に書き、書いた時点を記録に残す。
下は出発点の案であり、調整の途中で見直してよい。ただし最終比較を走らせたあとは変えない。

| 項目 | 測るもの | 却下の目安 | 採用の目安 |
| --- | --- | --- | --- |
| 2. 余裕 | 弾の種が現れてから、避けなければ当たる時刻までのフレーム数。体当たりは、進路が自機に向いてから当たるまで | 最小が 20 フレーム未満（著者の言う不意打ち） | 中央値が 40 フレーム以上 |
| 3. 不意打ち | 余裕が 20 フレーム未満の状況での死亡が、全死亡に占める割合 | 2 割以上 | 5% 以下 |
| 4. 迎撃の幅 | 編隊の各機に前方ショットを当てられる、自機の x の幅と時間の長さ | どの機かに当てられる位置が無い | 全機に、幅 2 単位以上・15 フレーム以上 |
| 5. 全滅率 | 全滅優先のボットでの全滅の割合 | 能力の高いボットで 1 割未満（事実上不可能）、または能力の低いボットで 9 割以上（安全すぎる） | 能力の高いボットで 5〜9 割 |
| 6. 追加リスク | 全滅優先と生存優先のボットの、死亡率の差 | 差が無い（リスクを取る意味が無い）、または全滅優先がほぼ必ず死ぬ | 差があり、全滅優先でも過半が生き残る |
| 7. ずらし耐性 | 成功した操作の時刻を ±6 フレーム、位置を ±1 単位ずらしたときの成功率 | 2 割未満（一点でしか成立しない） | 5 割以上 |
| 移動の要求 | 全滅に必要な自機の移動の速さ | 0.6／フレームを超える | 0.6 の 7 割以下で足りる |

評価用の seed は、設計と調整に使うものと、最終比較に使うものを分ける。最終比較の seed は、最終比較まで走らせない。

## 成果物

8 案の仕様、実行可能な実装、自機位置を変更できる比較再生、試験結果、採用・保留・却下の判断を提示せよ。

- 仕様と判断は `docs/` に置く。却下した案も、却下の理由と局面を残す。
- 比較再生は、ブラウザで開けるページとする。案と seed を選び、自機の位置を変えて同じ編隊を再生できること。
- 採用した案だけをゲーム本体に入れる。保留・却下した案の実装は、比較再生から呼べる形で残すか、消すかを判断して書く。
- 作業の最後に `npm run check` を通す。

## 著者の依頼文から直した点

| 直した点 | 理由 |
| --- | --- |
| 「原作の確認値」を「このゲーム自身の定数」とし、スターフォース由来の値は仮定と明記 | スターフォースの確認済みの数値は手元に無い。確認していない値を確認値と書かないため |
| スクロールと「画面外の敵は撃たない」を条件に追加 | 自機の移動で編隊が画面から出入りする。元の依頼文の「画面端」は固定画面を前提にしている |
| 弾の出方（種が敵に乗る、倒すと消える）を条件に追加 | 射撃規則と「予兆から回避期限までの余裕」の定義が、これで変わる |
| ロックオン、編隊全滅ボーナス、中型・大型の弾幕、ランク、タッチ操作を条件に追加 | 元の依頼文は編隊だけを単独で扱っている。このゲームでは同時に起きる |
| 予測可能性（項目 1）はボットで直接測れないと明記し、代用の指標を定義させる | 測れないものを測ったことにしないため |
| いまのボットが人を過小評価していること、結果は案の間の比較に使うことを追加 | 著者のプレイ報告とボットの結果が食い違っている |
| 採用基準の出発点の数値を追加 | 元の依頼文は「先に固定する」とあるが、数値が無い。数値はすべて制作エージェントの案である |
| 実装の置き場所と、プローブ、`npm run check` を追加 | このリポジトリの規則 |

設計条件、評価の 7 項目、却下の条件、成果物の骨子は、著者の依頼文のままである。
